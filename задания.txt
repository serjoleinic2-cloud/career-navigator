Я бы не интегрировал TaskContent через runtime_controller. Наоборот — runtime вообще не должен знать, как отображаются задачи. Runtime отвечает за состояние прогресса, а UI читает контент из уже существующего SkillNode.tasks.

ВАЖНО

TaskContent — immutable content.

Runtime не хранит TaskContent.

Runtime хранит только

active node

progress

scores

completed state

UI получает

SkillNode

↓

TaskContent

↓

Render

Таким образом сохраняется разделение:

Runtime Layer
отвечает за состояние

Content Layer
отвечает за содержание задач

Presentation Layer
отвечает за отображение

ОЖИДАЕМЫЙ РЕЗУЛЬТАТ

JourneyHeader

↓

↓

↓

Signals

↓

↓

↓

↓

↓

Bottom Navigation

Никаких изменений в Runtime Architecture.

Никакого дублирования Task Engine.

Только замена presentation layer с generic задач на реальные TaskContent.

Это решение соответствует архитектуре, которую вы выстраивали после консолидации:

Runtime Layer — состояние (прогресс, активная нода, оценки).
Content Layer — SkillNode + TaskContent (неизменяемые данные).
Presentation Layer — JourneyScreen (рендер и взаимодействие).

Такое разделение позволит в будущем легко добавлять новые профессии: достаточно будет создать новые ProfessionModule с SkillNode.tasks, а JourneyScreen останется универсальным и не потребует изменений.

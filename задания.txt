Правильная интеграция — не создавать второй state внутри React. React должен быть только представлением (view), а onboarding_engine.ts — единственным владельцем состояния (state authority). Это соответствует той архитектуре, которую вы уже приводили в порядок.

Я бы дал Opencode такое задание.

IMPLEMENTATION PATCH — OnboardingScreen Integration (Single State Authority)

Цель:
Создать рабочий OnboardingScreen без дублирования state management.

ВАЖНО:
Не создавать useReducer/useState для хранения onboardingState.
Единственный source of truth — существующий onboarding_engine.ts.

Архитектура

onboarding_engine.ts
        │
        │ owns OnboardingState
        ▼
OnboardingScreen
        │
        ▼
React UI

React хранит только render tick.

──────────────────────────────────

1. OnboardingScreen

Создать:

src/screens/OnboardingScreen/OnboardingScreen.tsx

Экран не хранит onboardingState.

Допустимо хранить только:

const [, rerender] = useState(0);

или

const [tick, setTick] = useState(0);

для перерисовки.

──────────────────────────────────

2. Получение состояния

НЕ делать:

const [state, setState] = useState(...)

НЕ копировать onboardingState в React.

Использовать существующий engine:

getOnboardingState()

или аналогичный accessor.

Каждый render читает состояние напрямую из engine.

──────────────────────────────────

3. Изменение состояния

Все действия пользователя идут ТОЛЬКО через engine.

Например:

selectProfession(...)

setExperience(...)

toggleGoal(...)

setTimeline(...)

togglePreference(...)

nextStep()

previousStep()

finishOnboarding()

Если подобных функций нет —
добавить их В onboarding_engine.ts.

НЕ создавать такую логику внутри компонента.

──────────────────────────────────

4. Обновление UI

После любого вызова engine:

setTick(v => v + 1)

или

rerender(v => v + 1)

React ничего не вычисляет.

Он просто перечитывает состояние из engine.

──────────────────────────────────

5. Validation

НЕ писать validation в компоненте.

Перед next:

const result = nextStep();

или

const result = validateCurrentStep();

Если validation не прошла:

показать сообщение.

Вся логика остается внутри:

onboarding_validation.ts

onboarding_flow.ts

──────────────────────────────────

6. Завершение onboarding

После Step 7:

finishOnboarding()

↓

startJourney(onboardingSnapshot)

↓

runtime initialized

↓

App переключается на JourneyScreen

OnboardingScreen не знает,
как создается runtime.

Он только вызывает engine.

──────────────────────────────────

7. App.tsx

App является только роутером.

При запуске:

if (runtimePersistence.hasRuntime())

    render JourneyScreen

else

    render OnboardingScreen

После finishOnboarding:

App автоматически начинает отображать JourneyScreen.

──────────────────────────────────

8. Запрещено

НЕЛЬЗЯ:

копировать onboardingState в React

использовать useReducer

создавать второй state manager

дублировать validation

дублировать onboarding flow

создавать отдельный wizard engine

──────────────────────────────────

9. Разрешено

Разрешается:

render tick

локальные состояния UI
(например открытый dropdown)

анимации

focus

scroll

НО не бизнес-состояние.

──────────────────────────────────

Результат

После патча:

onboarding_engine.ts
    ↓
единственный владелец состояния

OnboardingScreen
    ↓
тонкий UI

onboarding_flow.ts
    ↓
единственная логика переходов

onboarding_validation.ts
    ↓
единственная логика проверки

Без дублирования state management.
Без второй копии OnboardingState.

Именно такой подход хорошо сочетается с тем, что вы уже сделали ранее: сначала убрали дублирование runtime, затем сделали единый event bus. Следующий логичный шаг — сохранить тот же принцип и для onboarding: один движок владеет состоянием, UI только отображает его и вызывает команды. Это позволит избежать появления ещё одного "двойного источника истины", с которым вы уже боролись в runtime.
